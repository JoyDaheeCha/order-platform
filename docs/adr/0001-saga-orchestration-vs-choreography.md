# ADR-0001: Saga 구현 방식 — 오케스트레이션 vs 코레오그래피 (코레오그래피 채택)

- **상태(Status)**: Accepted (2026-06-27)
---

## 1. 맥락 (Context)

- 주문 도메인은 `Order → Payment → Inventory` 세 컨텍스트에 걸친 분산 트랜잭션
  - 단일 DB 트랜잭션으로 묶을 수 없으므로 **Saga**로 정합성을 맞춘다.
  - 모듈 간 통신은 **Kafka 메시지만 사용**
---

## 2. 결정 기준 (Decision Drivers)

| # | 기준 | 가중치 |
|---|------|--------|
| D1 | **학습 가치** — 보상·멱등성·타임아웃을 *명시적으로* 학습 가능한가 (todo.md 핵심) | 높음 |
| D2 | **흐름 가시성 / 디버깅** — Saga 진행 상태와 실패 지점을 추적하기 쉬운가 | 높음 |
| D3 | **결합도** — 컨텍스트 간 느슨한 결합(EDA 원칙) | 중간 |

| D5 | **확장성** — 단계 추가/변경이 쉬운가 | 낮음(학습 범위 고정) |

## 3. 고려한 방법 : 코레오그래피 vs 오케스트레이션

### 옵션 A — 코레오그래피 (Choreography) ✅ 채택

각 컨텍스트가 이벤트를 구독해 **자율적으로** 다음 동작을 수행한다. (중앙 조정자는 없다)
```
OrderCreated ─▶ [Payment] ─ PaymentCompleted ─▶ [Inventory] ─ StockDeducted ─▶ [Order] confirm
                  │                                  │
            PaymentFailed ─▶ [Order] cancel    StockShortage ─▶ [Payment] refund ─▶ [Order] cancel
```

**장점**
- 순수 EDA, 컨텍스트 간 결합 최소
- 인프라 단순 — 이벤트 토픽만 있으면 됨
**단점**
- 도메인간 이벤트 흐름이 한 눈에 안 보임
- 보상로직 분산(보상 트랜잭션 필요)
- 타임아웃 주체를 누가 관리할지 정해야한다. (예. 결제 요청후 타임아웃 여부는 누가 관리할것인지)
### 옵션 B — 오케스트레이션 (Orchestration) — 후속 학습 과제

**Saga Orchestrator**가 상태 기계로서 각 단계를 **커맨드 메시지**로 지시하고 결과 이벤트를 기다린다  
- 통신은 여전히 Kafka 비동기 메시지(직접 호출 아님).

```
        ┌─────────── OrderSagaOrchestrator (상태 기계) ───────────┐
        │  ProcessPayment ▶  ◀ PaymentCompleted/PaymentFailed     │
        │  DeductStock    ▶  ◀ StockDeducted/StockShortage        │
        │  (실패 시) RefundPayment ▶ , confirm/cancel Order        │
        └──────────────────────────────────────────────────────────┘
```

**장점**
- **Saga 전체 흐름 + 보상 + 타임아웃이 한 곳(상태 기계)에 명시적으로 모임
- 실패 시 "어디까지 했고 무엇을 보상할지"가 오케스트레이터 상태로 명확
- 타임아웃의 주체가 명확 — 오케스트레이터가 단계별 데드라인 관리

**단점**
- 오케스트레이터가 흐름을 알아야 함 → 컨텍스트 간 결합이 코레오그래피보다 높음
---

## 4. 결정
코레오그래피를 채택

근거:
- **규모 적합성**: 단계가 3개(결제·재고·확정)로 적다. 
- **실무에서 사용한 내용 깊이 학습**: 이직장 실무 경험과 동일하게 진행

---

## 5. 결과 / 영향

**긍정**
- 컨텍스트 간 결합 최소 — 새 구독자(추천·알림 등) 추가 시 발행자 무변경.
- 인프라 단순 — 이벤트 토픽만으로 구성(커맨드/리플라이 토픽 불필요).
- 순수 EDA·도메인 격리를 정석대로 학습.

**부정 / 주의 (= 의식적으로 설계해야 할 학습 포인트)**
- **흐름 비가시성**: Saga 진행 상태가 토픽에 흩어진다 → `orderNumber`를 전 이벤트의 상관관계 키로 강제
- **보상 분산**: 각 컨텍스트가 실패 이벤트를 구독해 자기 보상을 수행
- **타임아웃 감지 주체 부재**: 중앙 감시자가 없다 → **Order 컨텍스트에 데드라인 체커**(스케줄러/지연 메시지)를 두어, 기한 내 종료 이벤트가 없으면 취소를 트리거한다.
- **사용자 취소 경합(PC-4)**: 중앙 Saga 상태가 없어 "어디까지 진행됐나"를 Order가 자체 추적해야 한다 → Order Aggregate가 수신 이벤트로 진행도를 누적
